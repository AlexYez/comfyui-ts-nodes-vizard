# DualCLIPLoader: два текстовых энкодера в одном CLIP

## Назначение

`DualCLIPLoader` загружает два файла текстовых энкодеров и собирает из них один объект `CLIP` выбранной архитектуры. Типичный случай — Flux с CLIP-L и T5-XXL. Другие режимы используют свои пары: порядок и назначение файлов определяет семейство модели.

Нода нужна именно там, где архитектура ожидает два энкодера. Она не служит универсальным способом «усилить prompt» и не объединяет произвольные CLIP-модели по смыслу.

## Место в графе

Выход подключают к подходящей ноде кодирования текста. Для Flux official workflow использует `CLIPTextEncodeFlux`, которая принимает общий объект и отдельные строки для CLIP-L и T5-XXL. Полученный conditioning передаётся в sampling-цепь согласованной diffusion-модели.

`UNETLoader` и `VAELoader` загружают остальные компоненты раздельного комплекта. Если архитектуре нужен только один текстовый энкодер, достаточно `CLIPLoader`.

## Входы

`clip_name1` и `clip_name2` выбираются из локальных `models/text_encoders` и `models/clip`. Оба обязательны. Значения combo зависят от установленных файлов и не закрепляются в статье.

`type` сообщает ComfyUI, какую составную конфигурацию построить. В baseline доступны режимы SDXL, SD3, Flux, Hunyuan Video, HiDream, Hunyuan Image, Hunyuan Video 1.5, Kandinsky 5, LTXV, NewBie и ACE. Точный живой список показывает runtime overlay.

Необязательный `device` задаёт `default` либо `cpu`.

## Выходы

Нода возвращает один `CLIP`, а не два отдельных выхода. Внутри него находятся компоненты, tokenizer и правила кодирования, выбранные для `type`. Поэтому downstream-нода видит согласованную пару как единый объект.

Один общий тип порта не означает, что пары взаимозаменяемы. `clip_l + t5xxl` в режиме Flux и два Qwen-энкодера в режиме ACE создают разные конфигурации.

## Как работает

Имена разрешаются в два полных пути. Оба пути в заданном порядке передаются в `comfy.sd.load_clip`. Каждый tensor-файл безопасно читается вместе с metadata и, когда применимо, проходит преобразование старого quant-формата.

`CLIPType` определяет, как `load_text_encoder_state_dicts` распределит state dict между ожидаемыми компонентами. При `device=cpu` загрузка и offload закрепляются за CPU; при `default` действуют общие правила ComfyUI.

## Параметры и настройка

Сохраняйте не только имена файлов, но и их порядок, `type` и рекомендуемый quant-вариант из official workflow. У пары нет универсального «первого большого, второго малого» правила. Например, Flux обычно ставит `clip_l` первым и `t5xxl` вторым; в одном legacy official workflow встречается обратный порядок, поэтому переносить настройки следует целиком из конкретного графа.

CPU-режим полезен при нехватке VRAM, но два крупных энкодера могут занять много RAM и заметно замедлить encode. Если официальная поставка предлагает FP8/quantized файл, используйте именно совместимый вариант, а не случайно переименованный checkpoint.

## Проверенный пример

Рецепт «Раздельная загрузка Flux.1 Schnell» повторяет `DualCLIPLoader` № 40 из official `flux_schnell_full_text_to_image`: `clip_l.safetensors`, затем `t5xxl_fp16.safetensors`, `type=flux`, `device=default`. Выход по link 59 подключён к `CLIPTextEncodeFlux` № 41.

В том же workflow `UNETLoader` № 38 загружает `flux1-schnell.safetensors`. Рецепт сохраняет эту согласованную пару загрузчиков и связь CLIP с encoder. Prompt в fragment сокращён и помечен как редакционный, а имена компонентов и топология взяты из official JSON. Модели не исполнялись.

## Частые ошибки

**Файлы поменяли местами.** Верните порядок из workflow конкретной архитектуры; одинаковый тип combo не делает state dict симметричными.

**Выбран неверный `type`.** Загрузка может завершиться ошибкой либо построить объект, не соответствующий diffusion-модели.

**Один файл отсутствует.** Нода требует оба пути. Не подставляйте второй раз первый файл, если это прямо не предусмотрено моделью.

**Два одиночных `CLIPLoader` считают эквивалентом.** Они возвращают два независимых объекта и не собирают ожидаемую составную конфигурацию.

**Обычный `CLIPTextEncode` теряет часть возможностей.** Для ряда семейств требуется специализированная encode-нода с отдельными полями или дополнительными параметрами.

## Ограничения и производительность

Загрузка двух энкодеров требует прочитать оба state dict и разместить их по выбранной политике памяти. Это может быть дороже одного `CLIPLoader` и по RAM/VRAM, и по времени первого запуска. Длина двух текстовых входов также влияет на последующее кодирование.

Нода не проверяет, что файлы скачаны из одного model pack, и не знает смысловую совместимость по имени. Она также не уменьшает prompt и не смешивает его автоматически: это делает downstream encoder согласно архитектуре.
