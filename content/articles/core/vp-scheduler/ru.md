# VPScheduler: непрерывное VP-расписание сигм

## Что делает нода

`VPScheduler` строит одномерный tensor `SIGMAS` по непрерывной variance-preserving, или VP, формуле. Модель на вход не нужна: вся последовательность определяется четырьмя числами `steps`, `beta_d`, `beta_min` и `eps_s`.

Для `steps = n` создаётся сетка `t` из `n` равномерных точек от `1` до `eps_s`. Каждая точка превращается в сигму:

```text
sigma(t) = sqrt(expm1(beta_d × t² / 2 + beta_min × t))
```

После вычисленных значений нода добавляет отдельный ноль. Поэтому выход содержит `steps + 1` элементов и описывает `steps` переходов. При обычных положительных параметрах список идёт от большой сигмы к малой, затем к нулю.

VP здесь означает форму расписания, а не проверку совместимости с конкретной моделью. Нода не читает `model_sampling`, его диапазон сигм или архитектуру checkpoint.

## Когда использовать и когда не использовать

`VPScheduler` нужен в custom sampling, когда вы сознательно выбираете непрерывную VP-кривую и хотите управлять её коэффициентами напрямую. Он удобен для эксперимента с формой сетки: один и тот же список можно построить без загрузки модели, измерить и сравнить с Karras, exponential или модельным scheduler.

Не считайте VP универсальной заменой scheduler, рекомендованного автором модели. Начальная сигма по умолчанию около `152.17`, что заметно выше типичных границ многих моделей. Custom sampler сравнивает первый элемент с `model_sampling.sigma_max`, но это не превращает произвольную кривую в модельно согласованную.

Если требуется расписание из собственной таблицы модели, используйте `BasicScheduler` или `BetaSamplingScheduler`: они получают `MODEL` и выбирают сигмы с учётом `model_sampling`. Если нужен привычный диапазон `sigma_min`–`sigma_max` с явными границами, понятнее могут быть `KarrasScheduler` или `ExponentialScheduler`.

В 512 JSON официального пакета workflow 0.1.42, включая все вложенные subgraph, `VPScheduler` не найден. По этой причине статья не приписывает ему официально проверенную связку с определённым checkpoint.

## Короткий рецепт подключения

1. Добавьте `VPScheduler` и оставьте `beta_d = 19.9`, `beta_min = 0.1`, `eps_s = 0.001`.
2. Для первого чтения задайте `steps = 4`: короткий список легче проверить вручную.
3. Подключите выход `SIGMAS` к инструменту просмотра или к `SamplerCustomAdvanced` только после выбора совместимой модели и sampler.
4. Сверьте первую сигму с диапазоном модели, последнюю вычисленную сигму — с нулём перед ней, а длину — с ожидаемыми пятью элементами.
5. Меняйте один advanced-параметр за раз и сохраняйте исходный список для сравнения.

Fragment «Короткое VP-расписание» вставляет одну ноду с четырьмя шагами и настройками по умолчанию. Он не содержит модель и не запускает denoise. Это диагностический fragment, а не готовый workflow генерации.

При подключении к custom sampler добавьте обычные для него model, noise, guider, sampler и latent. Сам `VPScheduler` закрывает только порт `sigmas`.

## Входы, выходы и параметры

`steps` — `INT` от `1` до `10000`, по умолчанию `20`. Это одновременно число точек до конечного нуля и число sampler-переходов после его добавления. При `steps = 1` выход состоит из сигмы для `t = 1` и нуля.

`beta_d` — advanced `FLOAT` от `0` до `5000`, по умолчанию `19.9`, шаг `0.01`, без принудительного округления. Коэффициент умножает квадратичную часть `t² / 2`; его изменение особенно сильно влияет на верхнюю часть расписания.

`beta_min` — advanced `FLOAT` с теми же пределами, по умолчанию `0.1`. Несмотря на имя, это не нижний ограничитель через `clamp`. Параметр входит линейным слагаемым `beta_min × t`; фактическая предпоследняя сигма зависит также от `beta_d` и `eps_s`.

`eps_s` — advanced `FLOAT` от `0` до `1`, по умолчанию `0.001`, шаг `0.0001`. Это конечная точка сетки `t` перед добавленным нулём. При `steps = 1` `torch.linspace(1, eps_s, 1)` содержит только `1`, поэтому `eps_s` не влияет на результат.

Единственный выход — `SIGMAS`. При настройках по умолчанию и четырёх шагах exact-source probe получил приблизительно:

```text
[152.16698, 9.40320, 1.46197, 0.010486, 0]
```

## Типовые связки

Базовая цепочка custom sampling: `VPScheduler → SamplerCustomAdvanced`. В остальные входы sampler приходят `NOISE`, `GUIDER`, `SAMPLER` и `LATENT`. Нода расписания не заменяет эти компоненты и не задаёт CFG.

`SplitSigmas` или `SplitSigmasDenoise` можно поставить после VP, чтобы распределить расписание между двумя последовательными стадиями. Перед этим проверьте, что обе model-ветви понимают выбранный диапазон сигм.

Для сравнения кривых удобно держать рядом `KarrasScheduler`, `ExponentialScheduler` и `LaplaceScheduler` с одинаковым небольшим числом точек. Сравнивать только значение `steps` недостаточно: у Laplace в версии 0.32.0 ноль не добавляется, поэтому равные widgets дают разное число переходов.

`SetFirstSigma` способен заменить первую сигму уже готового VP-списка, но такая операция разрывает исходную формулу. Это инструмент намеренной коррекции, а не обязательный спутник scheduler.

## Практический пример

Для четырёх шагов параметры по умолчанию задают `t = [1, 0.667, 0.334, 0.001]` с учётом реальной float-сетки. Формула даёт четыре положительных значения, после чего `append_zero` добавляет пятое. Probe подтвердил форму `(5,)`, строгое убывание до нуля и приведённые выше числа.

При `steps = 1` получаются `[152.16698, 0]`. Здесь нет внутренней точки около `eps_s`: единственная точка линейной сетки равна началу `1`.

При `eps_s = 0` последняя вычисленная сигма тоже равна нулю, а `append_zero` добавляет ещё один. Для четырёх шагов хвост становится `[0, 0]`. Это создаёт дополнительный нулевой интервал и редко нужно намеренно.

При `eps_s = 1` все `steps` точек `t` равны единице. Результат — несколько одинаковых сигм `152.16698` и конечный ноль. Если одновременно обнулить `beta_d` и `beta_min`, выражение внутри `expm1` везде равно нулю, поэтому весь список, включая добавленный элемент, состоит из нулей.

## Частые ошибки и способы проверки

**`beta_min` принят за минимальную сигму.** В исходнике нет ограничения `sigma ≥ beta_min`. Посчитайте предпоследний элемент по формуле или сравните вывод при изменении `eps_s`.

**Ожидалось ровно `steps` значений.** VP добавляет ноль. Для `steps = 20` длина должна быть `21`, а число переходов — `20`.

**`steps = 1` не реагирует на `eps_s`.** Это свойство `linspace` с одной точкой. Для проверки влияния конечной точки используйте хотя бы два шага.

**В конце два нуля.** Такое происходит при `eps_s = 0`: ноль вычисляется формулой и затем добавляется ещё раз. Верните малое положительное `eps_s`, если дублирование не было запланировано.

**В списке появились `inf`.** Верхние пределы интерфейса намного шире безопасного диапазона float32 для этой экспоненциальной формулы. Exact-source probe с `beta_d = beta_min = 5000` дал бесконечности в верхней части. Уменьшайте коэффициенты и проверяйте `isfinite` до запуска sampler.

**Кривая формально корректна, но результат модели плох.** Сверьте первую сигму и весь диапазон с рекомендованным scheduler конкретной модели. Отсутствие входа `MODEL` — не преимущество совместимости, а отсутствие автоматической привязки.

## Производительность и внутреннее поведение

Нода создаёт два коротких CPU-tensor: сетку `t` и результат. Вычисления линейны по `steps` и включают квадрат, `expm1` и квадратный корень. При обычных десятках шагов их стоимость мала по сравнению с одним проходом diffusion-модели.

Выход создаётся на CPU, поскольку `device` не передаётся и функция использует значение по умолчанию. Дальнейший sampling сам согласует данные со своим вычислительным путём. При `steps = 10000` размер всё ещё невелик, но столь длинное расписание означает до десяти тысяч дорогих model-вызовов downstream.

Численная устойчивость зависит от показателя экспоненты. `torch.special.expm1` точно работает около нуля, однако при больших положительных аргументах float32 переполняется. Runtime разрешает значения до `5000`, не выполняя проверку конечности.

Значения не зависят от seed, batch или модели. При одинаковых параметрах scheduler детерминирован.
