# ModelMergeBlocks: раздельно смешать input, middle и out

## Что делает нода

`ModelMergeBlocks` смешивает diffusion-веса двух моделей разными коэффициентами для ключей, начинающихся с `input`, `middle` и `out` после удаления префикса `diffusion_model.`. Для выбранной группы формула такая же, как у простого merge:

`result = ratio × model1 + (1 − ratio) × model2`.

Следовательно, значение 1 берёт соответствующую группу из первой модели, а 0 — из второй. Названия групп проверяются как буквальные префиксы state-dict ключей; нода не анализирует смысл слоёв нейросети.

## Когда использовать и когда не использовать

Нода подходит прежде всего для совместимых UNet-подобных checkpoint, где ключи действительно называются `input_blocks…`, `middle_block…` и `output_blocks…`. Она позволяет, например, оставить входные блоки первой модели, смешать середину пополам и взять выходные блоки второй.

Не переносите этот рецепт автоматически на DiT, Flux, видео- или другую архитектуру с иными именами ключей. Для всех несовпавших префиксов используется fallback-коэффициент, а не отдельный анализ структуры. Если нужен один коэффициент для всей diffusion-модели, `ModelMergeSimple` проще и яснее.

## Короткий рецепт подключения

1. Подайте совместимые checkpoint в `model1` и `model2`.
2. Поставьте `input = 1`, чтобы входные блоки брать из первой модели.
3. Поставьте `middle = 0,5` для равной смеси middle-блоков.
4. Поставьте `out = 0`, чтобы output-блоки брать из второй модели.
5. Сравните результат с обеими исходными моделями на неизменном workflow.

Fragment `input из model1, middle пополам, out из model2` отражает эту схему. Он source-derived: точного `ModelMergeBlocks` в официальных templates 0.1.42 не найдено.

## Входы, выходы и параметры

- `model1`, `model2` (`MODEL`) — модели одной совместимой архитектуры.
- `input` (`FLOAT`, 0…1, по умолчанию 1) — доля `model1` для ключей, начинающихся с `input`.
- `middle` (`FLOAT`, 0…1, по умолчанию 1) — доля `model1` для префикса `middle`.
- `out` (`FLOAT`, 0…1, по умолчанию 1) — доля `model1` для префикса `out`, включая обычные `output_blocks`.
- `MODEL` — клон первой модели с ленивыми patch-операциями.

Порядок runtime-входов зафиксирован как `model1`, `model2`, `input`, `middle`, `out`. Wizard берёт его из `/object_info`.

## Типовые связки

Классический тракт: два checkpoint loader → `ModelMergeBlocks` → sampler или save. CLIP и VAE выбираются отдельно. Для единого коэффициента используйте `ModelMergeSimple`; для переноса разности — `ModelMergeSubtract → ModelMergeAdd`.

Сопоставление групп реализовано поиском самого длинного подходящего префикса среди переданных keyword-аргументов. В текущей runtime-схеме префиксы не пересекаются, но сам алгоритм допускает более длинное совпадение, если набор аргументов когда-либо расширится.

## Практический пример

Exact-source probe создал четыре ключа: `input_blocks` со значениями 2 и 10, `middle_block` — 4 и 20, `output_blocks` — 6 и 30, `time_embed` — 8 и 40. При `input = 1`, `middle = 0,5`, `out = 0` получены 2, 12 и 30 для трёх групп.

`time_embed` не совпал ни с одним из трёх префиксов и получил default ratio 1, то есть остался равен 8 из `model1`. Отдельный вызов exact-метода с другим порядком keyword-аргументов сделал первым `middle = 0,5`, и тот же unmatched-ключ стал равен 24. Штатный runtime передаёт входы в объявленном порядке, но это наблюдение важно для API-вызовов и показывает, что fallback зависит от порядка kwargs.

## Частые ошибки и способы проверки

- Коэффициент прочитан как доля `model2`. На самом деле 1 означает `model1`, 0 — `model2`.
- Названия `input/middle/out` приняты за универсальную карту любой архитектуры. Проверьте реальные ключи checkpoint.
- Unmatched-ключи забыты. В штатном порядке они получают значение `input`, потому что это первый числовой kwarg.
- Модели имеют разные формы. Как и в simple merge, вес первой модели сначала масштабируется, а несовместимое добавление затем пропускается с warning.
- CLIP и VAE считаются частью block merge. Они не обрабатываются.

Для проверки нужны список ключей, консоль без shape warnings и серия одинаковых seed для обеих крайних конфигураций и промежуточного merge.

## Производительность и внутреннее поведение

Нода проходит по key patches второй модели, обрезает строку `diffusion_model.`, выбирает самый длинный префикс из kwargs и регистрирует strengths `(1 − ratio, ratio)`. Патчи вычисляются позднее при загрузке весов.

Сам цикл по ключам дешёв по сравнению с materialization двух моделей. Память зависит от loader, offload и числа вложенных patches. Длинная merge-цепочка труднее воспроизводится; для итогового артефакта храните исходные версии, коэффициенты и точный ComfyUI commit.

## Совместимость, изменения и статус

Проверена версия ComfyUI 0.32.0 с frontend 1.48.7. Embedded docs 0.5.9 описывают «вклад второй модели», но exact код использует каждый параметр как долю первой. Документация также не раскрывает буквальный prefix-match и fallback первого kwargs.

Нода не deprecated и не experimental, replacement entry отсутствует. В полном wheel из 512 JSON прямых кейсов нет; recipe подтверждён source/runtime и тензорным probe, а не запуском checkpoint.

Редактор пока не проверил материал вручную.

## Связанные ноды и источники

`ModelMergeSimple` применяет один ratio ко всем совпадающим diffusion-ключам. `ModelMergeAdd` и `ModelMergeSubtract` предназначены для алгебры дельт, а не block-presets.
