# StableCascade_StageB_Conditioning: передать prior из Stage C

## Что делает нода

`StableCascade_StageB_Conditioning` добавляет результат Stage C в метаданные `CONDITIONING`, которое будет подано модели Stage B. Для каждого элемента conditioning она:

1. оставляет embedding `t[0]` без изменений;
2. создаёт поверхностную копию словаря `t[1]`;
3. записывает в копию `stage_c["samples"]` под ключом `stable_cascade_prior`;
4. возвращает новый список элементов.

Нода не смешивает тензоры, не усредняет prompt и не запускает VAE. Она передаёт ссылку на готовый prior через служебное поле. Модель `StableCascade_B` читает именно `stable_cascade_prior`, переносит его на устройство текущего noise и использует как conditioning `effnet`.

Копия словаря неглубокая. Вложенные объекты в metadata остаются общими с исходным conditioning, а сам prior не клонируется. Исходный верхнеуровневый словарь при нормальном выполнении не меняется.

## Когда использовать и когда не использовать

Подключайте ноду между sampling Stage C и positive-входом sampler Stage B. Она связывает две стадии: Stage B получает не только текстовое conditioning, но и изображённый Stage C prior.

Для sampler Stage C эта операция не нужна. Не подавайте сюда незавершённый пустой `stage_c`, если ждёте передачу уже сгенерированной композиции: в обычной цепочке вход `stage_c` приходит с выхода первого sampler. Пустой prior технически допустим, но не несёт результата Stage C.

Нода не заменяет `CLIPTextEncode`. Вход `conditioning` должен быть сформирован заранее. Она также не обрабатывает negative автоматически. В шести проверенных официальных Stable Cascade workflows через неё проходит positive, а negative подключён к sampler Stage B напрямую.

## Короткий рецепт подключения

В приложенном fragment сохранена официальная text-to-image топология:

1. `StableCascade_EmptyLatentImage.stage_c` идёт в первый `KSampler`.
2. Positive от `CLIPTextEncode` подаётся и в sampler Stage C, и в `conditioning` этой ноды.
3. Результат sampler Stage C подаётся в `stage_c`.
4. Выход `CONDITIONING` подключается к positive sampler Stage B.
5. `StableCascade_EmptyLatentImage.stage_b` служит начальным latent второго sampler; negative идёт туда без этой обёртки.

Fragment представляет внешние positive для двух мест отдельными портами, потому что формат Wizard пока не описывает fan-out одного external input. После вставки подключите к ним один и тот же исходный positive, как в официальном графе.

## Входы, выходы и параметры

- `conditioning` — обязательный `CONDITIONING`. Обычно это список пар `[embedding, metadata]` от Stable Cascade CLIP.
- `stage_c` — обязательный `LATENT`. Реализация обращается только к ключу `samples`.
- `CONDITIONING` — новый список той же длины, где у каждого элемента есть metadata-ключ `stable_cascade_prior`.

Widgets у ноды нет. Она не принимает strength, start/end percent или настройку смешивания. Любое прежнее значение `stable_cascade_prior` в metadata перезаписывается новым тензором.

Дополнительные поля словаря `LATENT` — например, `noise_mask` или `batch_index` — не переносятся. Они не удаляются из исходного `stage_c`, а просто не читаются этой операцией.

## Типовые связки

В официальной папке `ComfyUI_examples/stable_cascade` нода встречается во всех шести проверенных PNG: text-to-image, image-to-image, два image-remixing графа, canny ControlNet и inpaint ControlNet. Во всех случаях её выход идёт в positive `KSampler` Stage B, а вход `stage_c` — с результата `KSampler` Stage C.

Исходное positive conditioning во всех шести случаях одновременно используется в ветви Stage C и на входе этой ноды. Negative Stage B подключается напрямую. Так сохраняется текстовый prompt, а prior добавляется только там, где его ожидает positive-ветвь официальной схемы.

В workflow wheel 0.1.42 точных применений нет. Это результат просмотра всех 512 JSON и вложенных subgraph, а не выборочной проверки по имени файла.

## Практический пример

Пусть conditioning содержит два элемента, а `stage_c["samples"]` имеет форму `2 × 16 × 24 × 24`. На выходе останутся два прежних embedding. Для каждого появится отдельный верхнеуровневый metadata-словарь, но оба ключа `stable_cascade_prior` будут ссылаться на один и тот же tensor.

Безопасная проба точного метода подтвердила это поведение. Два embedding сохранили идентичность; два metadata-словаря были скопированы; вложенный тестовый словарь остался общим; исходное conditioning не получило нового ключа. Поле `batch_index` из входного `LATENT` не перешло в conditioning. Вызов с `stage_c = {}` завершился `KeyError`, потому что ключ `samples` обязателен фактически, а не только по соглашению.

Совпадение batch следует проверять до Stage B sampling. Официальная пустая нода создаёт `stage_c` и `stage_b` с одним `batch_size`, поэтому базовый рецепт согласован изначально.

## Частые ошибки и способы проверки

**Второй sampler игнорирует композицию Stage C.** Раскройте связи: результат первого sampler должен идти в `stage_c`, а выход этой ноды — в positive второго sampler. Подключение одного пустого `stage_b` prior не передаёт.

**В `stage_c` нет `samples`.** Такое бывает после custom-node с нестандартным payload. Откройте runtime-карточку предыдущей ноды или вставьте просмотр словаря; точный метод выбрасывает `KeyError`.

**Перепутаны positive и negative.** Сравните с официальной топологией. Через `StableCascade_StageB_Conditioning` проходит positive; negative Stage B приходит напрямую от текстового conditioning.

**Batch Stage C и Stage B различается.** Проверьте первые измерения обоих latent. Внутренняя модель переносит prior на устройство noise, но нода подготовки не выравнивает batch и не повторяет элементы.

**Ожидалось копирование `noise_mask` или `batch_index`.** Эта нода читает только `stage_c["samples"]`. Метаданные самого `LATENT` нужно обрабатывать отдельно, если они нужны другой части графа.

**После дальнейшего изменения вложенного metadata поменялась исходная ветвь.** Копирование поверхностное. Не мутируйте общий вложенный объект custom-нодой либо сделайте явную изоляцию перед такой операцией.

## Производительность и внутреннее поведение

Стоимость самой ноды зависит от числа элементов conditioning, а не от числа значений в prior. Она создаёт новый Python-список и по одному небольшому metadata-словарю на элемент. Большой tensor Stage C не копируется.

Копия prior может появиться позже: `StableCascade_B.extra_conds` вызывает `.to(device=noise.device)`. Если tensor уже находится на нужном устройстве, PyTorch способен вернуть тот же storage; при переносе с CPU на GPU потребуется память и передача данных.

Внутри Stage B prior становится `effnet`. Архитектура интерполирует эту карту до пространственной формы рабочего latent. Это не означает, что произвольные размер и batch безопасны: пространственный размер адаптируется в модели, а batch по-прежнему должен соответствовать цепочке.

## Совместимость, изменения и устаревание

Статья проверена на ComfyUI 0.32.0 и frontend 1.48.7. Нода активна, не experimental, не deprecated, не `api_node` и не `dev_only`. Формальных alias и replacement-записей для неё нет.

Schema fingerprint охватывает два обязательных входа, один выход, модуль и флаги. Но служебный ключ `stable_cascade_prior` виден только в Python-реализации. При обновлении недостаточно сравнить названия сокетов: нужно проверить имя metadata-ключа и то, как `StableCascade_B` его читает.

Embedded docs 0.5.9 правильно описывает общую передачу prior, но не фиксирует поверхностное копирование, перезапись существующего ключа и игнорирование прочих полей `LATENT`. Русская версия также начинается со служебной фразы о переводе и переводит runtime-имена; здесь системные идентификаторы оставлены без изменений.

## Связанные ноды и источники

- `StableCascade_EmptyLatentImage` создаёт парные начальные latent для text-to-image.
- `StableCascade_StageC_VAEEncode` создаёт Stage C prior из исходного изображения и нулевой Stage B latent.
- `KSampler` сначала формирует prior Stage C, затем использует подготовленное positive в Stage B.
- `CLIPTextEncode` поставляет исходное Stable Cascade conditioning; эта нода дополняет его, а не заменяет.

Операция копирования сверена с `nodes_stable_cascade.py`, потребление prior — с `StableCascade_B.extra_conds` в `model_base.py`. Топология и направление positive/negative подтверждены шестью официальными PNG на закреплённом commit. Модельный sampling с весами не выполнялся.
