# CLIPMergeAdd: сложить веса двух CLIP

## Что делает нода

`CLIPMergeAdd` клонирует `clip1` и для каждого совместимого ключа прибавляет полный вес `clip2`. Для общих параметров формула равна `clip1 + clip2`. Это арифметическая сумма, не среднее и не мягкое смешивание.

Выход сохраняет архитектуру, tokenizer и настройки первого CLIP. Нода пропускает параметры с окончаниями `.position_ids` и `.logit_scale`; они остаются от `clip1`. Ключи, которых нет в первой модели, patcher не принимает.

Операция особенно полезна после `CLIPMergeSubtract`: к target encoder можно добавить разность `tuned − base`. Сложение двух полных обычных encoder без такой подготовки часто даёт веса с удвоенным масштабом и непредсказуемый conditioning.

## Когда использовать и когда не использовать

Используйте ноду как арифметический шаг в проверенной merge-схеме, где `clip2` представляет осмысленную дельту. Типичный замысел: получить изменение между fine-tuned и исходным encoder, затем перенести его на родственный target.

Не применяйте `CLIPMergeAdd` вместо `CLIPMergeSimple`, если нужна смесь 50/50. У Add нет коэффициента: оба общих веса входят с множителем `1`. Для двух полных моделей среднее задаётся `CLIPMergeSimple` с `ratio = 0.5`.

Все три CLIP в delta-transfer должны быть совместимы по архитектуре и формам. Математическая запись `target + tuned − base` имеет смысл лишь тогда, когда одинаковые ключи обозначают одни и те же слои.

## Короткий рецепт подключения

1. Подайте fine-tuned encoder в `clip1` ноды `CLIPMergeSubtract`, его исходную базу — в `clip2`, `multiplier = 1`.
2. Подайте target encoder в `clip1` ноды `CLIPMergeAdd`.
3. Соедините результат Subtract с `clip2` ноды Add.
4. Выход Add используйте в `CLIPTextEncode` и сравните с target без дельты.
5. Если перенос слишком сильный, меняйте multiplier в Subtract, а не ищите отсутствующий strength у Add.

Shared fragment «Перенести разность tuned − base на target CLIP» используется статьями Add и Subtract. Он содержит две merge-ноды и три внешних `CLIP`; полного workflow, checkpoint names и encode-ветви нет.

## Входы, выходы и параметры

`clip1` и `clip2` принимают `CLIP`. Числовых параметров нет. Выход — один `CLIP`, list-семантика выключена. Runtime search alias — `combine clip`.

Внутри нода вызывает `clip1.clone()`, затем `clip2.get_key_patches()`. Для каждого ключа, кроме `.position_ids` и `.logit_scale`, регистрируется patch с `strength_patch = 1` и `strength_model = 1`. Exact patcher сначала сохраняет текущий вес первого входа, затем добавляет вес второго.

Если `clip2` уже несёт patches, `get_key_patches` возвращает структуру с базовым tensor и его patch-цепочкой. Перед сложением она рекурсивно вычисляется, поэтому Add прибавляет фактический вес второго объекта, а не только его последний patch.

Ключи только первого encoder остаются без изменения. Ключи только второго не создаются в клоне. При одинаковом имени и разных формах ComfyUI пишет предупреждение и не складывает этот tensor.

## Типовые связки

Главная связка семейства: `CLIPMergeSubtract(tuned, base) → CLIPMergeAdd(target, delta) → CLIPTextEncode`. На общих обычных весах при multiplier `m` результат равен `target + m × (tuned − base)`.

Для непосредственного сложения двух полных encoder можно подключить два loader-выхода прямо в Add, но сначала стоит проверить нормы весов и conditioning. У ноды нет нормализации, clipping или автоматического деления на два.

`CLIPSave` способен сохранить полученный encoder после материализации patches. До записи проверьте prompt-набор и лицензионные условия всех исходных моделей; сам рецепт Wizard файл не сохраняет.

## Практический пример

Полный recursive scan 512 JSON-файлов пакета 0.1.42 не нашёл `CLIPMergeAdd` ни в root, ни в `definitions.subgraphs[*].nodes`. Shared recipe поэтому помечен как source-derived, а не официальный case.

Exact-source probe использовал веса `[2, 4]` и `[10, 20]`. Node зарегистрировал пару коэффициентов `(strength_model = 1, strength_patch = 1)`, а точная `calculate_weight` вернула `[12, 24]`.

Probe также подтвердил, что `.position_ids` и `.logit_scale` не попадают в `add_patches`, а output clone сохраняет tokenizer `clip1`. Реальные CLIP weights и полный delta-transfer fragment не исполнялись.

## Частые ошибки и способы проверки

**Add принят за усреднение.** Проверьте формулу: `A + B`, без деления. Для среднего используйте Simple с `ratio = 0.5`.

**После сложения conditioning получил слишком большие значения.** Скорее всего, в `clip2` подана полная модель, а не дельта. Обойдите Add, затем соберите `tuned − base` через Subtract.

**Delta построена в обратном порядке.** `base − tuned` переносит изменение с противоположным знаком. Подпишите три внешних входа и проверьте контрольную формулу до запуска.

**Target использует другой tokenizer или размер слоёв.** Output всегда наследует tokenizer target как `clip1`, но веса delta должны совпасть по смыслу и форме. Одного совпадения части ключей недостаточно для качественного переноса.

**Служебные параметры не сложились.** `.position_ids` и `.logit_scale` намеренно остаются от первого входа. Это фильтр реализации, а не ошибка загрузки.

**Цепочка Add поверх Add стала непрозрачной.** Запишите алгебру каждого шага. Несколько полных сумм быстро увеличивают масштаб и усложняют поиск источника артефактов.

## Производительность и внутреннее поведение

Node создаёт clone wrapper и регистрирует patches; полная сумма вычисляется позднее при загрузке весов. Начальный проход линейный по числу ключей `clip2` и не выполняет text encode.

Во время материализации common weight нужен tensor первого encoder и рассчитанный tensor второго. Если второй сам состоит из patch-цепочки, ComfyUI рекурсивно вычисляет её перед сложением. Глубокая merge-цепочка увеличивает время подготовки и пиковую память.

Исходные объекты не меняются. Выходная обёртка имеет собственный список патчей, но `CLIP.clone` оставляет общими базовую модель и токенизатор. Поэтому выход нельзя считать независимой глубокой копией первого входа.

У Add нет быстрого bypass-параметра. Если прибавление не требуется, соедините target напрямую, чтобы не обходить state dict и не удерживать второй CLIP.

## Совместимость, изменения и устаревание

Статья проверена для ComfyUI `0.32.0`, frontend `1.48.7`, модуль `comfy_extras.nodes_model_merging`. Runtime fingerprint: `sha256:a4dfb835bc8fe0717417abc5373cdc72918b90786a3773311f171dca46aa1fcc`.

Нода не помечена как deprecated, experimental или API node. В Node Replacement API записи нет. Backend mapping связывает exact NodeId `CLIPMergeAdd` с Python-классом `CLIPAdd`; это нормальное различие registry ID и имени класса, не alias статьи.

Embedded docs 0.5.9 верно сообщают о клонировании первого входа и добавлении patches второго, но не предупреждают, что это полная сумма без нормализации. В статье численная семантика сверена с patcher implementation.
