# Save3DAdvanced: файл в output с камерой и pass-through

## Что делает нода

`Save3DAdvanced` сохраняет готовый `File3D` в постоянную папку `output` и не обрывает 3D-ветвь. После записи она возвращает тот же объект файла, сведения о трансформации модели, состояние камеры, `width` и `height`. Одновременно frontend открывает сохранённую копию во встроенном 3D-просмотрщике.

Слово Advanced относится к набору состояния и выходов, а не к более качественному кодированию. Backend не разбирает геометрию и не меняет контейнер. GLB остаётся GLB, OBJ — OBJ, STL — STL. Файл копируется под новым именем, составленным из `filename_prefix`, счётчика и исходного `File3D.format`.

Нода помечена как `output_node = true`, поэтому может завершать ветвь, хотя у неё есть пять обычных выходов. Это позволяет сохранить результат один раз, показать его и продолжить обработку без повторного загрузчика.

## Когда использовать и когда не использовать

Выбирайте `Save3DAdvanced`, когда вместе с постоянным файлом нужно сохранить логическую непрерывность графа: передать дальше выбранную камеру, transform metadata и размер viewport. Типичная пара — `Load3DAdvanced → Save3DAdvanced`, где все структурные выходы загрузчика можно соединить с соответствующими входами save-ноды.

Нода принимает готовые mesh-файлы: GLB, GLTF, FBX, OBJ, STL, USDZ и общий `FILE_3D`. Тензорный `MESH` она не кодирует. Для MESH используйте `SaveGLB`; для splat и point cloud предусмотрены отдельные save-ноды с более узкими runtime-типами.

Не подавайте сюда файл ради смены формата. Запись является копированием. `width` и `height` тоже не изменяют геометрию, текстуру или разрешение файла: frontend использует их как целевой размер и соотношение сторон viewport, а backend возвращает числа без вычислений.

Если нужен только просмотр без постоянной output-копии, подходит `Preview3DAdvanced`: он пишет временный файл. Если нужны `IMAGE`, `MASK` или normal pass, используйте `Load3D` либо отдельный renderer.

## Короткий рецепт подключения

Source-derived fragment строится по точной схеме 0.32.0:

1. Подайте готовый `FILE_3D` во вход `model_3d`.
2. Оставьте `filename_prefix = 3d/ComfyUI`.
3. Живой Load3D-виджет сформирует обязательный `viewport_state`.
4. Для первой проверки оставьте `width = 1024` и `height = 1024`.
5. Не подключайте optional `model_3d_info` и `camera_info`, если нужен fallback из текущего viewport.
6. После запуска возьмите первый выход `model_3d` для следующего 3D-узла, а камеру и transform metadata — из соседних выходов.

В workflow wheel 0.1.42 точного `Save3DAdvanced` нет. Поэтому рецепт не переносит чужие `widgets_values`, не подставляет вымышленную камеру и не прикладывает полный workflow. Обязательное состояние viewer создаётся frontend во время работы.

## Входы, выходы и параметры

`model_3d` принимает объединение `FILE_3D_GLB`, `FILE_3D_GLTF`, `FILE_3D_FBX`, `FILE_3D_OBJ`, `FILE_3D_STL`, `FILE_3D_USDZ` и общего `FILE_3D`. Это объект-обёртка над путём или бинарным потоком, а не строка пути и не `MESH`.

`filename_prefix` по умолчанию равен `3d/ComfyUI`. Итоговое имя имеет вид `<prefix>_00001.<format>` — без дополнительного подчёркивания перед точкой, которое использует `SaveGLB`. Подпапка остаётся внутри `output`; попытка выйти из неё отклоняется общей функцией ComfyUI.

`viewport_state` — обязательный `LOAD_3D`. Frontend сериализует текущие `camera_info` и `model_3d_info` в это поле. Если backend получает не словарь, он заменяет значение пустым объектом.

`model_3d_info` — optional advanced-вход типа `LOAD3D_MODEL_INFO`. Любое значение, отличное от `None`, имеет приоритет над viewport, включая пустой список. `camera_info` типа `LOAD3D_CAMERA` работает по тому же правилу.

`width` и `height` — обязательные `INT`: по умолчанию `1024`, диапазон `1…4096`, шаг `1`. Они выходят дальше без изменения. Frontend вызывает `setTargetSize`, который хранит оба числа и отношение `width / height`, затем перестраивает viewport.

Порядок выходов: `model_3d`, `model_3d_info`, `camera_info`, `width`, `height`. Первый выход — тот же входной Python-объект, а не новый `File3D`, указывающий на сохранённую копию.

## Типовые связки

`Load3DAdvanced → Save3DAdvanced` передаёт файл, transform metadata, камеру и размеры. Так положение модели и выбранный ракурс не теряются между интерактивной загрузкой и постоянной записью.

`Preview3DAdvanced → Save3DAdvanced` подходит для контрольной точки: preview создаёт временную копию, затем save-нода пишет постоянную. Оба узла могут передавать одинаковый набор состояния, но каждый frontend-виджет хранит собственные properties.

Первый выход `model_3d` можно направить в следующий процессор либо ещё одну save-ноду с другим префиксом. Это не чтение заново: в пределах выполнения передаётся исходный объект. Физическая output-копия при этом уже создана как side effect.

`SaveGLB` — более простой терминальный вариант. Он умеет кодировать `MESH`, зато не возвращает обычные выходы. Для готового File3D обе ноды копируют байты; различаются filename pattern, viewport и pass-through-контракт.

## Практический пример

Exact-source probe создал memory-backed GLB с тестовыми байтами, подключил viewport со своей камерой и transform metadata, а затем передал явные optional-значения. Нода была выполнена с `width = 800`, `height = 600` и префиксом `3d/advanced`.

В `output` появился `3d/advanced_00001.glb`; сохранённые байты совпали с входными. Выход `model_3d` сохранил object identity. Камера и model info на выходах пришли из optional-входов, а не из viewport, что подтверждает точный порядок приоритета. UI-result содержал путь к output-файлу, итоговую камеру и итоговый список transform metadata.

После выполнения frontend загружает output-путь, ждёт завершения текущего поколения загрузки и только затем применяет камеру и первый элемент `model_3d_info`. Это защищает viewer от позднего результата старого файла. Полный WebGL-сеанс и перенос fragment в живой graph probe не выполнял, поэтому пример не отмечен как целиком исполненный.

Exhaustive census дал ноль случаев `Save3DAdvanced` в 512 JSON и 768 root/subgraph graphs. Рецепт опирается на runtime, backend и frontend, а не на соседнюю топологию обычного `SaveGLB`.

## Частые ошибки и способы проверки

**MESH не подключается к `model_3d`.** Здесь нужен `File3D`. Сначала превратите MESH в файл либо сохраните его через `SaveGLB`.

**Камера из viewport исчезла.** Проверьте optional `camera_info`: даже явно переданное пустое или неполное значение перекрывает fallback. Для `model_3d_info` пустой список также считается явным override.

**Файл сохранён, но camera/model info пусты.** Нода не требует, чтобы `viewport_state` был содержательным словарём. При неготовом frontend-виджете backend всё равно копирует файл, а состояние становится `None` и `[]`.

**Изменение `width` и `height` не изменило модель.** Эти числа управляют target viewport и проходят в outputs. Они не масштабируют вершины и не меняют текстуры.

**Файл получил неверное расширение.** Для stream-backed `File3D` producer должен выставить `format`. При пустом значении save helper выбирает `.glb`, не проверяя содержимое.

**GLTF или OBJ открылся без ресурсов.** Основной файл копируется отдельно. Проверьте `.bin`, `.mtl`, изображения и относительные пути; нода не собирает их в пакет.

**После каждого запуска появляются новые файлы.** Это output-нода с числовым счётчиком. Pass-through не отменяет запись; bypass или отключение ветви нужны, если повторный экспорт нежелателен.

## Производительность и внутреннее поведение

Backend не парсит mesh и не выполняет GPU-операции. Основная работа — одно полное копирование `File3D`. Disk-backed источник переносится через `shutil.copy2`, stream-backed — последовательным чтением и записью. Большой файл временно существует как минимум в исходном и output-месте.

Сохранённая копия не становится первым выходом. Downstream получает исходный объект, поэтому его чтение идёт из первоначального пути или потока. Для потока `File3D.save_to` перед копированием возвращает позицию в начало; последующий `get_bytes` делает то же.

Runtime inventory показывает скрытые `prompt` и `extra_pnginfo`, но shared helper их не читает. В отличие от MESH-ветви `SaveGLB`, нода не встраивает workflow metadata и сохраняет байты без изменения.

Frontend добавляет вторую заметную стоимость: читает output-файл через HTTP и разбирает его в Three.js viewer. В `model_3d_info` backend может передать список, однако pinned frontend применяет к отображаемой модели только первый элемент списка.

## Совместимость, изменения и устаревание

Проверочная пара — ComfyUI 0.32.0 и frontend 1.48.7. Exact NodeId — `Save3DAdvanced`, module — `comfy_extras.nodes_save_3d`, category — `3d`. Нода экспериментальная и output-node; `deprecated`, `dev_only` и `api_node` равны `false`. Replacement API не содержит этот ID.

Schema fingerprint: `sha256:9fd5832dfd489f2549aef43574b13f09f2e91dcd72ae3dd0bdb8a847845d9fdb`. Особенно чувствительны список File3D-типов, порядок пяти выходов и контракт `LOAD_3D`.

Frontend-регистрация `Comfy.Save3DAdvanced` находится в общем модуле Load3D. Тип включён в lazy-load registry 1.48.7, получает виджет `viewport_state`, минимальный размер viewer, callbacks размеров и восстановление output-пути.

Embedded docs 0.5.9 передаёт общую роль ноды, но формулировка «контроль размеров вывода» может создать впечатление о перекодировании. В закреплённом коде размеры относятся к viewport и pass-through, а файл копируется без конвертации.

## Связанные ноды и источники

`Load3DAdvanced` создаёт File3D и структурное состояние без `IMAGE`-проходов. `Preview3DAdvanced` показывает тот же набор данных через temp-копию. `SaveGLB` подходит для терминальной записи и дополнительно кодирует MESH. `SaveGaussianSplat` и `SavePointCloud` используют тот же helper, но ограничивают семейство входного файла.

Материал сверялся с `nodes_save_3d.py`, `File3D`, `PreviewUI3DAdvanced`, frontend `load3d.ts`, embedded docs 0.5.9 и полным recursive census workflow wheel 0.1.42. Probe подтвердил byte-preserving output, имена, object identity, optional precedence и UI-result; сторонние viewers, связанные ресурсы и человеческое утверждение ещё не проверены.
