# ResolutionBucket: группировка latent-тензоров по точному размеру

## Что делает нода

`ResolutionBucket` разворачивает внутренние batch входных latent-тензоров по отдельным образцам, берёт у каждого последние два размера `(H, W)` и собирает одинаковые пары в общие batch. Соответствующий `CONDITIONING` переставляется вместе с образцом.

Нода не меняет разрешение и ничего не округляет. Значения `H = 4` и `H = 5` всегда образуют разные группы, даже если различие кажется малым.

## Когда использовать и когда не использовать

Нода полезна перед пакетной обработкой или сохранением набора, в котором образцы уже имеют несколько точных latent-размеров. Она уменьшает число внешних элементов, объединяя совместимые образцы через `torch.stack`.

Не используйте её для resize, crop, выбора целевых bucket-размеров или исправления несовместимых тензоров. Она не приводит каналы и дополнительные измерения к общей форме. Если нужны правила вроде округления до кратного 64, их надо применить до этой ноды.

## Короткий рецепт подключения

1. Подайте параллельные списки в `latents` и `conditioning`.
2. Проверьте не только внешние длины, но и число conditioning внутри каждого latent-batch.
3. Убедитесь, что тензоры с одинаковыми `H` и `W` совместимы по всем остальным измерениям.
4. После исполнения посмотрите число bucket и формы `samples`.

Фрагмент «Сгруппировать LATENT и CONDITIONING по размеру» оставляет оба входа внешними. Официального workflow с `ResolutionBucket` в пакете 0.1.42 нет; fragment не импортировался и не запускался.

## Входы, выходы и параметры

`latents` — обязательный списочный вход `LATENT`. Для каждого элемента код ожидает словарь с ключом `samples`; первый размер этого тензора считается batch.

`conditioning` — обязательный списочный вход `CONDITIONING`. Внешняя длина должна совпадать с длиной `latents`. Затем для каждого batch-индекса `i` код берёт `cond[i]`, но отдельной проверки внутренней длины нет.

Выходы снова называются `latents` и `conditioning` и имеют `output_is_list = true`. Параметров размера, округления, сортировки или минимального наполнения bucket у ноды нет.

## Типовые связки

`MakeTrainingDataset` может дать по одному latent-словарю на внешний `IMAGE`; `ResolutionBucket` объединит словари одинаковой геометрии. Результат можно направить в `SaveTrainingDataset`, учитывая, что один внешний LATENT после группировки уже содержит несколько образцов.

После `LoadTrainingDataset` группировка тоже возможна, если сохранённые элементы сохранили ожидаемую структуру. Нода доверяет каждой паре и не сверяет семантическое соответствие текста изображению.

В проверенных официальных шаблонах реального топологического примера нет. Эти связки следуют из runtime-типов и точного исходника.

## Практический пример

Пять образцов с latent-размерами `4×6`, `4×6`, `8×6`, `4×6`, `5×6` превращаются в три bucket. Их batch-размеры будут `3`, `1` и `1`; conditioning сохранит порядок `0, 1, 3`, затем `2`, затем `4`.

Изолированный прогон закреплённого метода дал формы `[3, 1, 4, 6]`, `[1, 1, 8, 6]` и `[1, 1, 5, 6]`. Порядок bucket соответствовал первому появлению каждого `(H, W)`, а не сортировке по площади или сторонам.

Это синтетическая проверка на тензорах, не исполнение fragment и не полный обучающий workflow.

## Частые ошибки и способы проверки

**Внешние длины различаются.** Реализация сразу выдаёт `ValueError`. Сравните число элементов `latents` и `conditioning`.

**Conditioning внутри batch короче.** При обращении к `cond[i]` возникает `IndexError`. Если conditioning длиннее, лишние элементы молча не используются. Проверяйте внутреннюю длину для каждого batch.

**Одинаковые `H` и `W`, но `torch.stack` упал.** Ключ bucket учитывает только два последних измерения. Разные каналы, временная ось или другая несовместимая форма при одном `(H, W)` приводят к `RuntimeError` во время stack.

**Пропал `noise_mask` или другое поле.** Выходной словарь создаётся заново только как `{ "samples": stacked_latents }`. Дополнительные ключи входного LATENT не переносятся.

## Производительность и внутреннее поведение

Сначала код создаёт плоские списки отдельных тензоров и conditioning, затем раскладывает их по словарю и для каждой группы вызывает `torch.stack`. Словарь Python сохраняет порядок первого появления ключей; элементы внутри группы тоже остаются в исходном порядке.

`torch.stack` создаёт новый тензор для каждого bucket, поэтому во время работы одновременно существуют исходные batch, ссылки на отдельные образцы и новые объединённые тензоры. Память зависит от общего объёма latent-данных, а число операций stack — от числа уникальных пар `(H, W)`.

Пустые и одинаковые по внешней длине списки возвращают два пустых списка. Геометрических вычислений, округления, padding и интерполяции нет.
