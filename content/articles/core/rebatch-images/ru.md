# Rebatch Images: перегруппировать кадры IMAGE

## Что делает нода

`RebatchImages` принимает список IMAGE-батчей, разворачивает их в одну последовательность кадров и нарезает эту последовательность на новые батчи размером не больше `batch_size`. Порядок остаётся стабильным: сначала идут все кадры первого входного значения, затем второго и так далее.

Выход помечен как list-output. Это список IMAGE-тензоров, а не один IMAGE-тензор со всей последовательностью. Последняя порция может быть короче остальных.

Нода не масштабирует кадры, не меняет число каналов и не дополняет остаток копиями. Она отвечает только за границы batch-пакетов.

## Когда использовать и когда не использовать

Нода полезна между ветвью, которая выдаёт список IMAGE-значений, и потребителем, которому нужны порции определённого максимального размера. В видео-графе её можно использовать как сборщик декодированных кадров перед `CreateVideo`; в обработке изображений — как ограничитель числа кадров на один mapped-запуск.

Не используйте её для изменения разрешения, повторения кадров или выбора отдельного диапазона. Для resize предназначены `ImageScale` и родственные ноды, для повторения — `RepeatImageBatch`, для среза — `ImageFromBatch`.

Если кадры разных размеров должны попасть в одну порцию, сначала приведите их к общей форме. `RebatchImages` не делает это сама и остановится на `torch.cat`.

## Короткий рецепт подключения

1. Подключите IMAGE-поток к `images`.
2. Задайте максимальный `batch_size`.
3. Если результат идёт в `CreateVideo`, подключите выход `RebatchImages` к `images`, задайте fps и при необходимости AUDIO.
4. Проверьте, поддерживает ли downstream list-output, а не только обычный IMAGE-батч.
5. Убедитесь, что кадры внутри каждой будущей порции имеют одинаковые `H`, `W`, число каналов, dtype и устройство.

Fragment Wizard повторяет центральную часть официального Wan Dancer workflow: `RebatchImages` с `batch_size = 4096` перед `CreateVideo` с `fps = 30` и `bit_depth = 8`. Входные кадры и звук остаются внешними.

## Входы, выходы и параметры

`images` имеет тип `IMAGE`, а вся нода объявлена с `is_input_list = true`. Backend поэтому получает список IMAGE-тензоров. Каждый тензор имеет форму `[B, H, W, C]`; его кадры извлекаются срезами `img[i:i+1]`.

`batch_size` — `INT` от 1 до 4096, default `1`. Из-за list-семантики backend получает этот параметр списком и берёт `batch_size[0]`.

Выход типа `IMAGE` имеет `output_is_list = true`. Каждый элемент выходного списка — тензор формы `[B_chunk, H, W, C]`, где `B_chunk ≤ batch_size`. Нода не возвращает отдельную метаинформацию о первоначальных границах входных пакетов.

## Типовые связки

`VAEDecode` → `RebatchImages` → `CreateVideo` собирает декодированные кадры для видеоконтейнера. В mapped-обработке можно поставить `RebatchImages` перед дорогой IMAGE-нодой, чтобы управлять числом кадров в одной порции.

`RepeatImageBatch` → `RebatchImages` сначала создаёт повторы, затем режет их на порции. `RebatchImages` → `ImageFromBatch` позволяет выбирать кадры уже внутри каждого выходного пакета, но list-семантика downstream должна быть понятна пользователю.

Deprecated `ImageBatch` и современный `BatchImagesNode` соединяют обычные IMAGE-входы в один batch. Они не заменяют `RebatchImages`, когда вход уже представлен списком и нужен список новых порций.

## Практический пример

В официальном `video_wan_dancer.json` нода находится внутри subgraph `Image to Video (Wan Dancer)`. `VAEDecode` № 658 передаёт IMAGE по link `1329` в `RebatchImages` № 671. Сохранённый `batch_size` равен `4096`. Выход по link `1330` поступает в `CreateVideo` № 158 с параметрами `fps = 30` и `bit_depth = 8`.

Здесь 4096 работает как большой верхний предел: нода собирает доступные декодированные кадры, но не создаёт недостающие до 4096 и не гарантирует порцию такой длины.

Синтетический запуск точного класса получил два входных батча длиной 2 и 3 при `batch_size = 2`. Выход имел размеры `[2, 2, 1]`, а числовые метки кадров сохранили исходный порядок. Fragment повторяет официальные настройки центрального участка, однако целиком в интерфейсе ещё не исполнялся.

## Частые ошибки и способы проверки

**Downstream срабатывает несколько раз.** Это ожидаемо: выход является списком. Для одного обычного IMAGE-батча нужна другая схема сборки.

**Последняя порция короче заданной.** `batch_size` — максимум. Остаток не повторяется и не заполняется пустыми кадрами.

**`torch.cat` сообщает о разных размерах tensor.** Нода не делает resize. Все кадры внутри конкретного chunk должны иметь одинаковые `H`, `W` и `C`, а также совместимые dtype и device.

**Разные размеры иногда проходят, иногда падают.** Если граница формы случайно совпала с границей chunk, несовместимые кадры оказываются в разных выходных тензорах и ошибки нет. При другом `batch_size` они могут попасть в одну порцию. Приводите форму заранее, не полагайтесь на совпадение границ.

**Потерялось происхождение кадра.** После разворачивания нода не хранит номер исходного списка или пакета. Если эта информация нужна, ведите её по параллельной ветви.

## Производительность и внутреннее поведение

Реализация сначала создаёт Python-список одноэлементных срезов для каждого кадра. Затем для каждого chunk вызывает `torch.cat(..., dim=0)`. Даже порция из одного кадра проходит через `torch.cat`, поэтому появляется новый выходной tensor.

Большой `batch_size` уменьшает число выходных элементов, но увеличивает размер одной allocation и требования downstream. Малый размер снижает объём одного пакета, зато создаёт больше Python-объектов и mapped-запусков. Лучшее значение зависит от разрешения кадров, памяти и поведения следующей ноды.

Пик памяти включает исходные IMAGE-тензоры, список срезов и готовые chunks. Нода не освобождает или не выгружает кадры на CPU специально и не меняет layout данных.

## Совместимость, изменения и устаревание

Статья сверена с ComfyUI `0.32.0`, frontend `1.48.7` и модулем `comfy_extras.nodes_rebatch`. Runtime fingerprint: `sha256:c6a8bdbf23c861f5e80374fc61a76609c88e9556f7680da309da67dd4931fe06`.

Нода не помечена как experimental или deprecated. В официальном пакете 0.1.42 найдено одно вхождение: активная subgraph-нода в Wan Dancer. Корневых вхождений нет. Node Replacement API не объявляет для неё замену.

Встроенная документация 0.5.9 правильно называет выход списком батчей, но не описывает отсутствие resize и зависимость ошибки от границ chunk; эти детали подтверждены pinned-реализацией.

## Связанные ноды и источники
